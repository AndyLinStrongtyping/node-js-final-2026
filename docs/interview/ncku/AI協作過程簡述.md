# AI 協作過程簡述

在這次使用者系統 API 設計中，我先提供專案的後端程式碼合規檢查、驗證與授權流程檢查，以及 Node.js 課程複習簡報，讓 AI 了解專案背景與課程內容。接著，我提出註冊、登入及查詢使用者資料的需求，請 AI 協助整理 API endpoint 與資料表設計，最後再將內容簡化成報告。

在先前專案中，我也使用 AI 協助理解後端觀念、整理驗證與授權流程，以及檢查程式碼是否符合講義與 API 規格。依據目前提供的檢查資料，討論內容包含密碼雜湊、JWT 驗證、角色與資料所有權，以及 migration 和索引等需要補強的項目。

我的使用方式是先提供需求與相關資料，讓 AI 協助分析、提出建議，再由我確認內容是否符合專案情境。透過這樣的協作，我可以更快整理設計思路，也能把程式實作與背後的觀念連結起來，作為專案改善及面試準備的參考。

## 本次提問與討論節錄

以下保留主要提問與回覆重點，為討論摘要，並非完整逐字紀錄。先前專案的使用方式依本次提供的檢查資料概述。

### 1. API 設計

**我的提問：**提供三份參考資料，請 AI 設計使用者註冊、登入及查詢資料的 endpoint 與資料表。

**AI 協助：**提出 API 路徑、users 資料表、bcrypt 密碼雜湊、JWT 驗證與統一錯誤回應的設計，再依我的要求簡化成報告。

### 2. 一般使用者與管理員的差別

**我的提問：**「使用者不等於管理者對吧，所以她查詢資料只要查自己就好？」

**討論結論：**題目未要求管理員功能，先假設一般會員登入後只查自己。查詢對象由 JWT 驗證後的身分決定，不信任前端指定的使用者 ID。最初討論以 `/api/users/me` 表達本人資料，最後文件沿用既有專案的 `/api/users/profile`，功能範圍相同。

### 3. API 回應緩慢

**我的初步想法：**「回應錯誤、封包丟失、網址連結錯誤等等的都有可能？」並提出要寫錯誤處理程序。

**AI 協助釐清：**回應慢與回應錯誤需要分開判斷。應先量測資料庫、外部 API、網路及程式處理的耗時，再針對瓶頸改善。錯誤處理是必要的配套，無法單獨保證速度改善。

**我的追問：**「API 另外一端的資料回傳有問題對嗎？」

**討論結論：**外部 API 回應太慢或沒有回應，可能拖慢整體請求；資料格式錯誤則可能造成解析失敗，若觸發重試也可能增加時間。應設定等待期限、驗證回應並控制重試次數。

### 4. 500 萬筆 logs 的查詢

**我的初步想法：**程式直接把全部 log 查出來，應加上條件查特定資料。

**AI 協助釐清：**更精確地說，是讀取 `logs` 整張資料表，而非整個資料庫。除了查詢條件，還應選取必要欄位、分頁或限制筆數；若需處理全部紀錄，則分批讀取，以降低記憶體與傳輸負擔。

### 5. 文件整理與提交

**我的要求：**將討論過程與結論簡單整理，先上傳到自己的 GitHub，並確認題目是否只要求文件。

**討論結論：**題目細項明列 endpoint、Database Schema 與 Debug 分析，但總說明同時提到「設計與實作」及「提交程式碼」。因此文件未明確排除程式實作。本次依我的要求完成文件整理，並列出設計建議與既有程式的差異，避免將建議誤認為已完成的功能。
