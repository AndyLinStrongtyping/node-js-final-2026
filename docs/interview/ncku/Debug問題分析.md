# Debug 問題分析

## 一、API 回應時間約 3 秒

### 可能原因

API 回應緩慢可能來自資料庫、外部 API、網路或程式本身，單憑 3 秒無法判斷原因。

| 可能原因 | 說明 |
|---|---|
| 資料庫查詢緩慢 | 查詢資料量太大、缺少適合的索引，或等待資料鎖定 |
| 外部 API 回應緩慢 | 本身的 API 必須等待對方回傳，整體時間因此增加 |
| 網路延遲或封包丟失 | 資料傳輸延遲或重新傳送，增加等待時間 |
| 程式處理耗時或系統負載高 | 過多運算、重複查詢或資源不足 |

網址錯誤或回傳格式錯誤通常會造成失敗；如果伴隨連線等待或重試，也可能讓回應變慢。

### 解決方式

1. 記錄整個請求、資料庫查詢與外部 API 呼叫的耗時，先定位瓶頸。
2. 若是資料庫問題，縮小查詢範圍、限制筆數，並透過執行計畫評估索引。
3. 若是外部 API 問題，設定等待期限並檢查回應狀態與資料格式。只對適合重試的暫時性錯誤採用有限次數的重試，避免重複執行寫入操作。
4. 若是程式問題，減少不必要的運算與重複工作；適合延後完成的工作可改由背景工作處理。
5. 加入錯誤處理，對外回傳清楚且安全的訊息，將內部細節記錄在伺服器。

**結論：**錯誤處理能處理失敗情況，但改善速度仍需要量測並解決真正的瓶頸。

## 二、一次查詢 500 萬筆 logs

題目程式碼：

```php
$rows = DB::table('logs')->get();
```

### 可能發生的問題

這段程式沒有查詢條件或筆數限制，會嘗試一次取得 `logs` 整張表的所有欄位與資料列。當資料量達到 500 萬筆時，可能造成：

- 資料庫讀取與傳輸負擔增加，查詢時間過長。
- PHP 記憶體不足，導致執行失敗。
- 請求超時；若全部回傳前端，也會造成過大的回應與畫面負擔。

### 解決方式

- 加入日期、使用者或紀錄類型等查詢條件。
- 只選取需要的欄位。
- 畫面查詢採用分頁或限制筆數，避免一次載入全部資料。大量資料翻頁可評估游標分頁。
- 依篩選與排序需求檢查執行計畫，再評估適合的索引。
- 如果必須處理全部紀錄，使用 `chunkById()` 或 `lazyById()` 等方式分批處理，不要再把所有批次累積回同一個陣列。

**結論：**加查詢條件之外，也要限制每次取得的資料量。畫面查詢使用分頁，大量處理則採用分批讀取。
